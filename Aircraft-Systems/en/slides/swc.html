Slide 2: 13.2 Restrictions and catastrophic effects; airworthiness requirements

Modern aircraft run many millions of lines of code in dozens of computers, so software management control must define and document the development process to avoid catastrophic effects of unapproved changes uploaded to aircraft computers; example: flight control software failing during an IFR approach in zero visibility. Required artifacts include an airworthiness certification plan, software quality assurance plan, configuration management plan, configuration control procedures, code, design and requirements standards, development plan, verification plan, design and requirements documents, traceability, test cases and procedures, verification results, quality assurance and configuration management records, problem reports, and a software accomplishments summary. Airworthiness: "Software Considerations in Airborne Systems and Equipment Certification" was published in 1992 by RTCA as DO-178B and by EUROCAE as ED-12B; FAA and EASA use it as certification guidance. Five criticality levels by the consequence of an undetected software error: Level A catastrophic (multiple fatalities, loss of aircraft); B hazardous/severe (serious or fatal injuries to a smaller number of passengers); C major (reduced safety margin, impaired crew efficiency, discomfort or possible injuries); D minor (reduced margins well within crew capabilities, passenger inconvenience such as a routine flight plan change); E no effect. Flight control and navigation are flight critical and need Level A; cabin entertainment is Level E. Different levels do not normally run on the same processor unless an approved partitioning scheme such as ARINC 653 is used: a specification for space and time partitioning in a real-time operating system, used in integrated modular avionics (IMA). DO-178B was written when most code was hand-written; model-based design called for clarification.

Numbers: DO-178B/ED-12B published 1992; five levels A to E

Slide 3: 13.3 DO-178C and required traceability (Figure 13-1)

DO-178C was developed in 2011 to replace DO-178B, because model-based design needed clearer definitions between high-level system requirements and low-level software requirements and a process to verify model-based software; in July 2013 the FAA released Advisory Circular AC 20-115C recognising DO-178C as compliance with the software aspects of airworthiness regulations. Supplements: tool qualification (DO-330), model-based development and verification (DO-331), object-oriented technology (DO-332), formal methods (DO-333); tools such as MATLAB, Simulink and Embedded Coder support model-based design. Figure 13-1 shows the required tracing between certification artifacts: system requirements allocated to software, software high-level requirements, software low-level requirements, software architecture, source code, executable object code, test cases, test procedures, test results; red traces are required only for Level A, purple traces for Levels A, B and C, green traces for Levels A through D; Level E needs no traceability. Level A executable object code must be "robust with respect to the software requirements" so it responds correctly to abnormal inputs and conditions. The figure carries objective references such as A-3.6, A-4.6, A-4.8, A-5.5, A-7.3, A-7.4, A-7.9 and a legend with columns A, A B C, A B C D.

Numbers: DO-178C in 2011; AC 20-115C in July 2013; DO-330, DO-331, DO-332, DO-333

Slide 6: 13.6 Answers 13-1 to 13-6

Answer 13-1: the documents listed on page 13.2 (airworthiness certification plan through software accomplishments summary). Answer 13-4: ARINC 653 is a software specification for space and time partitioning in a real-time operating system that lets one processor host applications of different criticality levels; it is used in IMA systems to isolate flight-critical from non-flight-critical functions so that if one application fails it cannot take down the entire IMA system. Answer 13-2: DO-178 is a standards document on the safety of software in aircraft systems; it established design assurance levels based on safety assessment and hazard analysis of failure conditions; FAA and EASA use it as certification guidance. Answer 13-5: when DO-178B was published most software was hand-coded; the move to model-based automatic coding needed clarification between high-level system requirements and low-level software requirements, and a process to verify model-based software and decide whether model-based simulation or formal methods could replace some or all testing. Answer 13-3: flight control and navigation are flight critical and need Level A because failure may cause multiple fatalities and loss of aircraft. Answer 13-6: DO-178C Level A requires that traceability between the source code and the executable object code be documented.
